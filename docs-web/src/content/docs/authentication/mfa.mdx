When `require_mfa` is `true`, all users must complete an MFA step after password authentication before an authorization code is issued.

## MFA flow

```mermaid
sequenceDiagram
    actor User
    participant Browser
    participant IdP as Autentico

    User->>Browser: Enter username + password
    Browser->>IdP: POST /oauth2/login
    IdP->>IdP: Credentials valid — create MFA challenge
    IdP->>Browser: 302 → /oauth2/mfa?challenge_id=X
    Browser->>IdP: GET /oauth2/mfa (render MFA page)
    IdP->>Browser: Show TOTP input (or send email OTP)
    User->>Browser: Enter OTP code
    Browser->>IdP: POST /oauth2/mfa (code + challenge_id)
    IdP->>IdP: Validate OTP — mark challenge used
    IdP->>Browser: 302 → redirect_uri?code=AUTH_CODE
```

The MFA challenge is a short-lived, single-use token (5 minutes). If it expires, the user is redirected back to the login page.

A verified challenge is consumed before issuing a session, authorization code or trusted-device cookie. Concurrent submissions can succeed only once. Used, expired, exhausted or changed challenges are rejected; a database failure while consuming the challenge cannot complete login.

## TOTP (Authenticator App)

TOTP uses time-based one-time passwords compatible with any RFC 6238 authenticator app — Google Authenticator, Authy, 1Password, Bitwarden, and others.

**Enrollment** happens automatically on first login after MFA is enabled. Users who have not yet set up TOTP are shown a QR code on the MFA page:

{/* TODO: add screenshot of TOTP enrollment page (QR code) */}

1. Scan the QR code with an authenticator app
2. Enter the 6-digit code from the app to confirm enrollment
3. On all future logins, enter the code from the app

Each TOTP code can be accepted only once across browser login, password grants, and account actions. Enrollment confirmation also uses up its code, so wait for the authenticator to show the next code before signing in or disabling MFA. Codes use 30-second timesteps with one timestep of clock tolerance in either direction; a previously accepted or older timestep cannot be reused.

Enrolled TOTP has a shared account budget of five failed verifications across browser login, the password grant, and TOTP removal. Starting a new login challenge, changing IPs, or entering the correct password does not reset it. After five failures, even valid TOTP codes are rejected until `account_lockout_duration` expires (15 minutes when configured as zero or a negative duration). Successful TOTP verification resets the failure count. The account API and password grant return `403 mfa_locked` during lockout; the browser redirects to login with a cooldown message. Password failures on removal do not spend TOTP attempts.

The TOTP secret is encrypted per-user in the database with AES-256-GCM and the persistent `AUTENTICO_TOTP_ENCRYPTION_KEY` from `.env` or the environment. Schema 17 encrypts existing enrollments in place, so existing authenticator apps keep working. Keep the original encryption key when restarting or restoring the database. The QR code is generated server-side — no third-party service is involved.

**Issuer name** displayed in the authenticator app comes from the `theme_title` setting.

## Email OTP

Email OTP sends a one-time code to the user's registered email address on each login. No enrollment step is required.

To use email OTP, set:

```
mfa_method = email
```

And configure SMTP:

```
smtp_host = smtp.example.com
smtp_port = 587
smtp_username = auth@example.com
smtp_password = your-smtp-password
smtp_from = auth@example.com
```

<Aside type="caution">
Email OTP is only as secure as the user's email account. TOTP is generally preferred for stronger security.
</Aside>

## Enabling MFA

In the Admin UI: Settings → set `require_mfa` to `true` and choose `mfa_method`.

Via API:

```bash
curl -X PUT https://auth.example.com/admin/api/settings \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"require_mfa": "true", "mfa_method": "totp"}'
```

## Trusted devices

After a successful MFA verification, users can check **"Trust this device"** to skip MFA on future logins from the same browser. See [Trusted Devices](/authentication/trusted-devices/) for MFA bypass on recognized devices.

<Aside type="tip">
MFA is applied to password authentication only. Passkey authentication does not go through the MFA flow — a passkey is itself a strong second factor.
</Aside>
